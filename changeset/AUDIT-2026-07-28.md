# Independent production-readiness audit

This audit challenges the original changeset rather than treating its synthetic
tests as evidence of real-world accuracy.

## Findings that changed the implementation

1. `npm test` was quoted as `node --test "test/*.test.js"`, so Node looked for a
   literal file named `test/*.test.js` and the checked-in test command failed.
   It now uses a small cross-platform runner that enumerates `*.test.js` files;
   this works on both Node 20 and the supported Node 22+ runtime.
2. Verizon Connect Reveal redirects from `reveal.fleetmatics.com` to the current
   `login.us.vzconnect.com` login. The previous rules missed the final page.
   Current first-party URL markers and regression tests were added.
3. Samsara's `ai-assistant-styles.*.js` bundle is loaded on the public sign-in
   page. It cannot prove that a customer has Assistant enabled. The separate
   detection was removed; the product maps to the observable Samsara platform
   at `platform-level`.
4. XHR patterns such as `api\.openai\.com` matched attacker-controlled suffixes
   such as `api.openai.com.attacker.invalid`. XHR matches must now reach the end
   of the observed hostname.
5. The Samsara and Verizon priority `scriptSrc` patterns were unanchored and
   matched vendor names placed in an unrelated script path. They are now
   hostname-anchored.
6. The reported 96% is catalog reachability, not empirical live-scan coverage.
   The report now says `catalog-matchable` and separately counts retained
   `live-observed` evidence.
7. The claimed 518-domain DNS sweep did not retain its input corpus or raw
   output. Its markers are labelled `unreproduced-prior-sweep` until concrete
   domains are retained.
8. A real Reveal scan crashed when a cross-origin page denied access to
   `sessionStorage`. JS collection now skips inaccessible globals instead of
   aborting the entire scan.
9. Puppeteer 19 was unsupported and brought seven high-severity advisories.
   The runtime now uses Puppeteer 25.4.0, requires Node 22.12.0+, and audits
   cleanly.

## Follow-up on finding 4 (added after the audit)

The audit's XHR fix required a match to reach the **end** of the observed
hostname, which closed the `api.openai.com.attacker.invalid` suffix spoof. It did
not constrain where a match may **start**, so a pattern could still match
mid-label. Verified against the live catalog:

| Hostname | Before | Expected |
| --- | --- | --- |
| `nottome.app` | matched `Tome` | no match |
| `evil-tome.app` | matched `Tome` | no match |
| `zmeta.ai` | matched `Meta AI` | no match |
| `notfal.run` | matched `fal.ai` | no match |

Short single-label patterns such as `tome\.app`, `fal\.run` and `meta\.ai` were
affected; longer ones were not, and a few (`(?:^|\.)character\.ai`) already
guarded themselves by hand.

`isHostnameSuffix()` in `wappalyzer.js` now requires both ends to land on a DNS
label boundary: the match must reach the end of the hostname **and** begin at the
start of it, on a dot, or immediately after one. Both spoof classes are rejected
with no legitimate match lost — tenant subdomains (`tenant.api.openai.com`),
leading-dot patterns (`acme.wd5.myworkday.com` against `\.myworkday\.com`) and
mid-hostname patterns (`abc.chat.qbusiness.us-east-1.on.aws`) all still match.

The rule is deliberately scoped to `xhr` alone. `scriptSrc`, `html` and `url`
carry full URLs and free text, where a mid-string match is correct.

Two regression tests were added in `test/wappalyzer.test.js`
(`xhr patterns must start on a DNS label boundary` and
`the hostname suffix rule applies only to the xhr channel`), taking the suite to
197 tests.

## Release condition: the Node runtime is now pinned and enforced

Raised on review: `engines.node` declared `>=22.12.0` but nothing pinned or
enforced it. On a machine defaulting to Node 20.9 the unit suite passed while the
CLI died with `ERR_REQUIRE_ESM` from inside Puppeteer's module graph — a symptom
that names neither Node nor the version requirement.

Four layers now close it, because a pin that only lives in documentation is
decoration:

| Layer | File | Effect |
| --- | --- | --- |
| Version pin | `.nvmrc`, `.node-version` | `nvm use` / `fnm` / `asdf` resolve 22.12.0 |
| Install gate | `.npmrc` (`engine-strict=true`) | `npm install` refuses an unsupported runtime instead of warning |
| Runtime guard | `scripts/lib/engine.js` | Checked *before* Puppeteer is required |
| CI | `.github/workflows/ci.yml` | Matrix on the floor and current LTS, plus a job asserting Node 20.9 fails clearly |

`driver.js` throws for library consumers; `cli.js` catches and prints one line,
so the CLI does not dump a dependency stack trace. Verified on the real runtimes
installed on this machine rather than simulated:

```text
Node 20.9.0   Node 22.12.0 or newer is required, but this process is running
              Node 20.9.0. Puppeteer will fail to load with ERR_REQUIRE_ESM on
              older runtimes. Use the version in .nvmrc (nvm use) and reinstall
              dependencies.
              exit 1, no stack trace
Node 22.12.0  210/210 unit tests, 5/5 CLI smoke checks
Node 24.18.0  210/210 unit tests, 5/5 CLI smoke checks
```

The pin is the declared floor rather than the newest runtime, so CI proves
`engines.node` is honest — nothing in the code quietly needs a newer Node than
the package claims. `test/engine.test.js` additionally asserts the pin files
exist, agree with each other, satisfy `engines.node`, and that
`scripts/lib/engine.js` is in the published `files` list, since `driver.js`
requires it at load time.

`scripts/smoke-cli.js` is the missing coverage layer: it spawns the real CLI so a
broken require chain fails the build. `npm test` runs it.

## Second review: one regression and three evidence defects

Raised after the follow-up work. All four were valid.

**1. The subsumption rule deleted valid DOM detections.** It applied regex
substring logic to CSS selectors, where containment has entirely different
semantics — an id or class match is exact, not a prefix.

| Technology | Selector deleted | Wrongly assumed covered by |
| --- | --- | --- |
| Apple Pay | `script#apple-pay-shop-capabilities` | `script#apple-pay` |
| Asciinema | `div.asciinema-player-wrapper` | `div.asciinema-player` |
| Swiper | `div[data-swiper-slide-index]` | `swiper-slide` |

All three are restored and verified detecting. `dom` and `probe` are now excluded
outright, and the rule additionally applies only to **literal** patterns —
anything containing alternation, anchors, quantifiers, groups or classes is left
alone, because containment implies nothing about matching there either. Removals
fell from 40 to 18. Saving 40 regex evaluations was never worth a silent false
negative. `test/catalog.test.js` asserts no `dom`/`probe` pattern is ever dropped,
and `test/normalize.test.js` pins the three cases above.

**2. The DNS evidence claim contradicted the code.** `dnb-technologies.js`
hard-coded `verification: 'unreproduced-prior-sweep'`, so 37 targets kept that
label after the sweep became reproducible. Labels are now **derived** from
`data/dns-sweep-results.json` at load time, degrading to
`unverified-no-sweep-retained` if no sweep exists.

The "all 55 markers corpus-verified" claim was also wrong, because the test
compared technology *names* rather than exact technology-pattern pairs. Precisely:
48 markers are observed by their exact string, 5 are
`corpus-observed-via-equivalent` (Detectify, Dropbox, Segment, Mixpanel, DocuSign
— superseded during redundancy removal), 1 `live-observed`, 1
`official-documented`. The accurate statement is **all 55 enriched technologies
have at least one observed retained marker; five original pattern strings were
superseded**. The test now compares exact pairs.

**3. `1/85` was presented as an observation rate. It is not.** It is a yield
against a 29-page convenience corpus with no mapping from marker to a page where
its vendor is in use. Only 8 pages returned a clean 200 (12 were 304, one 403,
four recorded no status) while all counted as "scanned", and the driver aborts
non-document/script requests, which suppresses the follow-on application requests
that would have exercised other markers. Reported now as: *"1 of 85 markers
appeared in this 29-page corpus under the current request-aborting driver"*, with
the limitations enumerated in the output, the status distribution retained, and
the figure framed as a lower bound.

**4. The sweep was re-runnable but not auditable.** Results now carry a timestamp,
corpus SHA-256, marker-set SHA-256, resolver servers, Node version and platform.
Every domain is classified by resolution outcome (`ok`, `nodata`, `nxdomain`,
`servfail`, `timeout`) instead of collapsing every DNS error into "no records" —
the latest run is 513 `ok`, 23 `nodata`, 0 failures. `npm run sweep:check`
re-hashes both inputs and **exits non-zero when the retained results are stale**,
rather than merely printing them.

Also cleaned while verifying: three source files contained literal **NUL bytes**,
written accidentally by a code-generation step. They were functional but made
`grep` treat the files as binary, which is how the manifest's new-file count came
out blank. Replaced with printable separators.

## Third review: audit-integrity corrections

**1. The catalog delta was stale.** It reported 239 changed technologies while the
current semantic diff is 246, omitting seven entries the later dedup pass touched:
Apache Iceberg, Birdeye, Databricks (AWS), Microsoft Azure Site Recovery,
Salesforce Remedyforce, Salesforce SPF and ServiceNow Problem Management.

The root cause was that the delta was produced by ad-hoc commands and had to be
remembered whenever the catalog moved — it went stale twice. It is now generated by
`scripts/catalog-delta.js` (`npm run delta`), which materialises the base revision
from git and compares parsed entries. `npm run delta:check` fails when the
committed artifacts no longer describe the working tree, and
`test/catalog.test.js` runs that check, so this cannot drift again.

**2. "Via equivalent" was inferred from a shared technology name.** Any observed
marker for the same technology counted as evidence for any other. The five current
substitutions happened to be valid, but a technology can carry unrelated TXT
patterns — Zoho ships both `zoho-verification=` and a `\.zoho\.com` pattern, which
prove different things — so a future addition would have received false evidence.

Equivalence is now asserted only when the observed pattern is a **strict literal
substring** of the superseded token, which is exactly the subsumption relation that
removed it: any record matching the original also matches its substring. The
predicate is exported as `supersedes()` and unit-tested, including the rejection
cases. `EXPECTED_SUPERSESSIONS` documents the intended five, and a test asserts the
set is exactly Detectify, DocuSign, Dropbox, Mixpanel, Segment and that each
substitution passes the containment check.

**3. The "SHA-256" fields were truncated to 64 bits.** The digest was sliced to 16
hex characters while still being named `sha256`, overstating the provenance. The
full 64-character digest is now retained, with a test asserting the length.

**4. The manifest's file counts were scoped without saying so.** "8 modified and 35
new" describes the reviewable code subsets; the worktree holds 36 modified tracked
files (8 code/config + 28 catalog data) and 46 untracked files (35 source + 11
generated artifacts and this directory), plus 28 gitignored files under `backup/`.
The manifest now states all three figures and where each is described.

## Manifest counts corrected

Also raised on review: the manifest claimed 7 modified tracked files and 20 new
sections. Measured values were 8 and 22. Both are now derived from
`grep -c '^diff --git'` and cross-checked against `git diff --name-only`; the
